## Unexpected findings

1. **Overview 500 after a mobile "add exercise" — pre-existing, not 0019.**
   `ExecutionService._latest_exposure` (`be/src/agonez_api/modules/execution/service.py:1596`)
   puts `performance["exercise_unit_track_id"]` into `LatestExposureExercise.exercise_trace_id: int`;
   an exercise added during a mobile workout has no exercise track (NULL), so
   `GET /plan-runs/{id}/overview` fails validation (`latest_exposure.exercises.7.exercise_trace_id
   Input should be a valid integer`) as long as that workout is the run's latest. Reproduced
   identically on the unconverted database with `e79fc1d`. Production has **0** such rows today
   (`exec.exercise_unit_performances.exercise_unit_track_id IS NULL`), so it is latent: the first
   athlete who adds an exercise on the phone breaks the run's desktop overview. Not in scope here;
   needs its own fix.
2. **`live_mobile_execution_api_scenarios.py` is stale** (three issues in RB-06 step 2): it passes
   only with the patch, on runs with saved prescriptions. Not fixed here (docs-only task).
3. Nothing unexpected in 0019 itself: same results as T2.1's rehearsal and T2.3's golden counts.
