Every new column, the enum and the function carry a `COMMENT`.

**`plans.copy_revision_tree(source, target, regenerate_progression_ids)`**

- Checks, in order: no NULL argument (`null_value_not_allowed`, 22004); source revision exists and
  target revision exists (`no_data_found`, P0002); locks the target revision row
  `FOR NO KEY UPDATE`; target has no days (`object_not_in_prerequisite_state`, 55000, message
  "target revision N is not empty"). Copying a non-empty revision onto itself is therefore refused.
- Then one statement of chained data-modifying CTEs (one snapshot of the source): days → workout
  units → slots → target muscles → variants → sets. Each step joins its `RETURNING` rows back on
  (mapped parent, natural key). Rows are inserted in ordinal order, so new ids follow the plan order.
- Every column except `id` and the parent reference is copied as stored: lineage keys always,
  `load_step_kg` raw (NULL stays NULL), `icon`, `weekday`, `loading_mode/cycle` on slots and sets,
  `load_spec`, `rep_range_semantics`, `min_volume_level`, `active_working_set_*`,
  `progression_model_slug`, set `role`.
- `regenerate_progression_ids = false` keeps `progression_id`; `true` draws one new id per distinct
  source id (a materialised CTE), so shared loops stay shared and nothing is shared with the source.
- Returns one row per copied row, `entity` ∈ `day`, `workout_unit`, `exercise_slot`,
  `exercise_variant`, `set_infra`. Target muscles have no id and are not in the map.
- It does not care about revision status; the caller creates the target revision row first and owns
  the transaction.

**Migration timing** (dump `agonez_db_backup_2026-11-25.sql`: 10 revisions, 72 days, 46 workout
units, 315 slots, 7 runs; postgres:15 test container with `fsync=off`):

- 0018 alone, `psql` `BEGIN … COMMIT`, 3 runs on fresh restores: **15, 20, 15 ms**.
- `run_migrations()` on fresh restores (0017 → 0018), 5 runs: 36, 38, 33, 41, 52 ms; the same call

- The volatile `gen_random_uuid()` default rewrites `workout_unit_prescriptions` and

  milliseconds only. Production uses fsync, so expect somewhat more, still well under a second.

**Runner behaviour (checked).** `run_migrations` sends the whole file through
`connection.execute(sql)` without parameters, i.e. as one simple-protocol query string, so the
server parses the `$$` body itself, inside `connection.transaction()`. An error anywhere rolls back
the whole file, including the function and the type, and the version row is not written. Proven by
`test_an_error_anywhere_in_the_migration_rolls_all_of_it_back`.

## Deviations from the design

Small additions to `02` §2, whose SQL is conceptual; no contract or architecture change, docs not
edited:

- The function also refuses NULL arguments and a missing source or target revision, locks the
  target revision row, and raises with specific SQLSTATEs (22004, P0002, 55000) so callers can tell
  the cases apart.
- Entity names of the returned map are fixed as `day`, `workout_unit`, `exercise_slot`,
  `exercise_variant`, `set_infra`; target muscles are copied but not mapped (no id).
- The restored template holds only one RELEASED revision (25), so "several released revisions" became
  "every non-empty revision" (1 RELEASED, 9 DRAFT; the function ignores status). The dump has no
  fallback variants and no NULL `load_step_kg`; the builders plan covers both.

## For the next tasks

- **T1.2:** call it as
  `SELECT entity, source_id, target_id FROM plans.copy_revision_tree(%s, %s, %s)`. In psycopg the
  errors are `errors.ObjectNotInPrerequisiteState`, `errors.NoDataFound`,
  `errors.NullValueNotAllowed`. Python ints are adapted by value; ids are small today, but casting
  `%s::integer` avoids a "function does not exist" error should an int8 ever be sent.
- **`load_step_kg` changes for duplicates in T1.2:** today `_copy_draft_tree` copies the loaded value,
  which `_load_draft_rows` COALESCEs with the resistance-source default
  (`plans/repository.py` ~1279), so a duplicate stores the default explicitly. The function copies
  the raw NULL. Reads COALESCE either way, so API output is the same; T1.2's existing duplicate
  tests should not depend on the stored value.
- Lineage keys are untouched by today's draft save for existing rows (tested); new rows get the
  default. Nothing reads them yet.
- Copying into a revision of a library plan works too (the test uses the same plan's next
  RELEASED revision); `plan_revisions_one_draft_per_plan` still allows only one DRAFT per plan, so a
  caller creating a DRAFT target must not have another.
- The tree reader in the test file (`read_tree`, `assert_complete_copy`) is reusable for T1.2's
  fingerprint tests and for T2.1/T2.3 comparisons; move it to `builders.py` if a second test file
