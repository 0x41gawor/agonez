## What exists now

Test-only; no application code and no migration changed.

**`be/tests/integration/golden.py`** — capture, normaliser, allow-lists, comparison. Its docstring
is the reference for all of them.

| Name | What it does |
| --- | --- |
| `observation_scope(db, only=None) -> Scope` | Runs, observation dates, tracks, sessions and workouts, all read from the database (no hard-coded ids). |
| `settle(client, clock, scope)` | One reconciling read per run and of the run lists, before anything is compared. |
| `capture(client, db, clock, scope) -> Capture` | `{Read(run_id, kind, at): {status, etag, body}}`, normalised. Fails if an `exec` table or view is not covered. |
| `compare(before, after, allowed=(), mapping=None) -> Comparison` | Path-level diff. With `mapping` (the 0019 reference map) the plan-row ids of the "before" side are translated first. `require_clean(claim)`, `report()`, `summary()`. |
| `unanswered(capture)` | Non-prescription reads that did not answer 200. |
| `EXPECTED_AFTER_CONVERSION`, `ADDITIVE_FIELDS`, `added(kind, path, reason)` | The two allow-lists. |
| `save` / `load` / `mask_lineage_keys` | Baseline files for a re-run with later code. |

**What is read.** Per run, at each observation date: `overview`, `analysis/queue`, `microcycles`
(timeline), mobile `context` (with ETag). At the live date: `calendar`, `events`, `workout-traces`
and each trace, `load-series` (default; volume load with drafts), every exercise trace and `/next`.
Every session: saved prescription and fallback preview (error answers are compared too). Every
workout: mobile snapshot. Also the run's rows of all 14 `exec` tables and 6 `exec` views. Across
runs: desktop and mobile run lists, mobile context without a run id.

The **live date** is the run's earliest `scheduled` session (else `ends_on`); the observation dates
are that and every earlier microcycle start, so reading marks no further session as missed.

**Normaliser** (nothing else is removed; no id is dropped):

1. mobile context `generated_at` → `"<generated_at>"`;
2. `prescription_id` of a fallback preview for a session **without** a saved workout prescription →
   marker (the preview is rolled back, so each call draws a new sequence number; it must not be a
   saved id). With a saved prescription it is compared exactly;
3. "before" side only: values under the keys of `PLAN_ROW_ID_KEYS` (revision, day, unit, slot,
   variant, set) are replaced by their copy in `public.agonez_0019_reference_map`, per run and
   entity, then compared exactly. A converted run's id without an entry is reported. Runs not in the
   map (already owning a run plan) are not translated and get no allowed difference.

## Deviations from the design

- `06` T2.3 asks for an id-insensitive normaliser that removes database ids. As the task notes
  required, ids are **kept**: exec ids compared exactly, plan-row ids translated through the
  reference map. Feature fields are not removed but allow-listed by path and exact change.
- More reads than `06` T2.3 lists (calendar, events, exercise traces and `/next`, saved
  prescriptions, previews of all sessions, workout snapshots, run lists, `exec` tables and views).
- "Re-run after T3.1" needs a saved baseline (below): T3.1 code cannot read the "before" database.

Docs `00`–`07` not edited (test-only).

## Known gaps / follow-ups

- The golden test adds about 2.5 min to `pytest -m integration` (50 s → 3 min 12 s): about 4 800
  reads, mostly previews and exercise traces.
- Mobile context is not read for microcycles after the live date: that would mark sessions as missed.
  Future sessions are covered by their previews, the timeline, calendar and traces.
- Library reads (`/api/plans…`, run preview) and Atlas are not captured; T-MIG-07 covers the library
  rows byte for byte.
- Both dumps have no in-progress workout and no run owning a run plan; only the temporary test above
  exercised those.
- In baseline mode, a dump with a run still `scheduled` would show differing `run.version` values
  (`settle` stamps `updated_at` at each execution). Neither dump has one.
- Visible after the deploy (expected until T4.5): the run header and run list of every converted run
  show the run plan's new `P0xx` code, same name (as T2.2 already does for new runs).
