# PlanCreator prescription-metadata extension

## Objective

Close the PlanCreator prescription model by adding metadata required by a future
Plan-Execution module, without implementing load resolution, progression state, workout
history, or session execution.

## Existing canonical model

- A plan draft owns ordered days.
- A training day owns at most one workout unit.
- A workout unit owns ordered exercise slots (intent, role, targets, loading default).
- An exercise slot owns one default and optional fallback exercise variants.
- An exercise variant is the concrete exercise unit: it owns the Atlas exercise,
  progression model, and ordered set prescriptions. Its database `id` is already the
  stable backend identity independent of labels, exercise slug, and ordering.
- A set prescription currently owns rep range, numeric RIR, volume threshold, and loading
  mode/cycle metadata.

## Architecture decisions

1. Extend `plans.exercise_variants` with:
   - `progression_id uuid NOT NULL`, independently generated by default and shareable;
   - nullable `active_working_set_min` / `active_working_set_max`.
2. Extend `plans.set_infra_prescriptions` with:
   - a set-role enum;
   - a tagged JSON `load_spec` value;
   - rep-range semantics enum;
   - an RIR prescription enum supporting RIR0–RIR4, NOT_APPLICABLE, and UNDEFINED.
3. Preserve old records through migration defaults: working / absolute / undefined,
   numeric RIR values converted to their RIR enum equivalents, unique progression UUIDs.
4. Validate tagged load specifications in the API and validate set references at the
   exercise-variant boundary. References use the submitted set ordinal (`ref_set_idx`).
5. Treat ramp-up sets and sets without numeric RIR as non-evaluable in Analysis V1. Do not
   resolve active-set ranges or load specs.
6. Bump compact import/export to `agonez-plan-sanity-v4`; retain V1–V3 imports.
7. Use progressive disclosure in the editor:
   - set role remains visible because it changes the meaning of a set;
   - rep semantics and load specification live in a compact metadata drawer;
   - progression-loop sharing and variable active working sets live in an advanced
     exercise-unit panel;
   - sharing choices show `day / slot / exercise`, while persistence uses UUIDs only.
8. Deep-copy operations mint new progression UUIDs while preserving sharing relationships
   inside the copied subtree.

## Delivery sequence

1. Add migration and backend schemas/validation/persistence.
2. Extend resolver/export/import and keep Analysis V1 safe.
3. Add frontend types, editor transforms, validation, and advanced controls.
4. Update JSON V4 documentation and compatibility parsers.
5. Add migration/schema/repository/import-export/editor tests.
6. Run backend and frontend full suites, rebuild both containers, and verify a live
   create/save/export/import round trip.
